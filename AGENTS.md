# Writing the GitHub README

- Write for a mathematician opening the repository for the first time. Lead with a self-contained theorem, define its notation, and link the Lean statement and a human-readable proof. Keep each result family visible in the front-page survey with a proof link. Preserve worked examples and proof details in the linked notes.
- Use ordinary prose, italic variables and Unicode relations for short inline expressions. Put displayed equations in a fenced `math` block on separate lines, using elementary notation such as sums and fractions. Keep headings, link labels and tables readable without a math renderer.
- Avoid `\operatorname`, `\substack`, custom macros, TeX environments and prose embedded with `\text` in the README. Define a set or a function in the preceding sentence to simplify a long formula.
- When changing formulas, check the rendered GitHub Markdown. Inspect the equations for lost braces, literal commands, missing symbols and clipping at narrow widths. A math container in the HTML alone does not establish that its contents typeset correctly.
- Identify the scope of each result. Link kernel-verified theorems, paper deductions and finite computations to their respective evidence.
- After changing Lean statements, run `lake build` and then `NORMALITY_UPDATE_THEOREM_INDEX=1 lake env lean scripts/readme_theorems.lean` to refresh the collapsible declaration directory. Update the prose survey when a result adds a new family or strengthens a published conclusion.
- Register each major result in `docs/registry/<FAMILY>.toml` (format in `docs/registry/SCHEMA.md`); identifiers are permanent. Run `python3 scripts/portal.py build` after editing the registry, the benchmark suite, the topic map or a figure, and `python3 scripts/portal.py check` before committing. Figures are generated by `scripts/figures/build.py`; edit the generator, never the SVG.

# Standing Research Objectives and Benchmarks

- Pursue all four standing objectives specified in `docs/research-objectives.md` as independently valuable outcomes: (1) establish normality (full normality, simple normality, exact digit/word frequencies, joint uniformity, effective rates); (2) establish nonnormality (simple nonnormality, disjunctive nonnormality, membership in *K*<sub>*b*</sub>, exact digit-frequency bias); (3) quantify digit distributions (exact discrepancy, sharp gaps, frequency laws, limit measures, prescribed spectra, bounds *D*⁺ < 1 and *D*⁻ > 0); (4) establish rigorous mathematical limitations (barriers, excluded methods, undecidability).
- Maintain the permanent benchmark suite in `docs/benchmarks/classical-constants.toml` (fixed 50-constant roster `BC-01`…`BC-50`) and `docs/benchmarks/arithmetic-families.toml` (format and mechanical checks in `docs/benchmarks/SCHEMA.md`). Never add, remove, replace or renumber constants in the 50-constant roster; change a benchmark status only when a registered result or named published theorem establishes it, never from finite computations, conditional theorems, heuristics or cross-model reviews.
- Strictly separate evidence labels (`Kernel-verified`, `Lean-supported paper proof`, `Paper proof`, `Finite certificate`, `Conditional`, `External input`, `Open`), treat finite digit statistics as finite measurements only, and state explicitly that cross-model review is not independent human peer review.

# Build and Test Environment

- On Windows hosts, use the remote Linux build and test server `Hail` over SSH (host alias `hail` in `~/.ssh/config`, not WSL) for Lean 4 builds (`lake build`, `Audit.lean`, `leanchecker`, `readme_theorems.lean`), LaTeX manuscript builds, and Linux test/verification runs (`scripts/verify.sh`). Do not use WSL for builds or tests.
